# マルチエージェントでの作業手順

複数のエージェント (と人間) が同時に作業しても、作業が重複したり、マージが衝突したり、設計が食い違ったりしないようにするための手順です。判断の経緯は [ADR 0007](../adr/0007-multi-agent-workflow.md)。

## 役割

| 役割 | 仕事 |
| --- | --- |
| **オーケストレーター** | タスクの起票と分割、割り当て、ブランチのマージ、ADR の承認。人間か、リードのエージェントが務める |
| **ワーカー** | 割り当てられた 1 タスクを、1 つの worktree で完了させる |
| **レビュアー** | ワーカーのブランチを読み、受け入れ条件と規約を満たしているかを確認する |

ワーカーは自分でタスクを選んでもかまいません (次の「着手」の手順に従ってください)。

## タスクのライフサイクル

```
todo ──(着手)──► in-progress ──(完了報告)──► review ──(マージ)──► done
                     │
                     └──(依存の未完了・設計上の問題)──► blocked
```

### 1. 選ぶ

`just tasks` を実行すると、`ready` (状態が todo で、依存するタスクがすべて done) のタスクが表示されます。その中から選びます。

- 同じクレートを触る `in-progress` のタスクがあるものは、なるべく避けます。
- タスクファイルの `crates:` が、そのタスクで触ってよい範囲です。

### 2. 着手する

```sh
# main の作業ツリーで: タスクファイルの状態を更新して、すぐにコミットする (担当の宣言)
#   status: in-progress
#   assignee: <エージェント名やセッション名>
git commit -m "chore(tasks): start T0104" docs/tasks/T0104-*.md

# worktree を作る (ブランチ task/T0104-<タスクファイルの slug> も作られる)
just wt-add T0104
cd .worktrees/T0104
```

`just wt-add` (`scripts/worktree.mjs`) は次のことを行います。

- `git worktree add .worktrees/<ID> -b task/<ID>-<slug> main`
- main の作業ツリーの `target/` をコピーする。ワークスペースのクレートの incremental キャッシュは除き、更新時刻は保つ。これにより依存クレートのビルドを省ける (実測: 最初からビルドすると約 120 秒、コピーすると約 20 秒)
- `pnpm install --offline` を実行する (Git フックが worktree 内の `node_modules` を使うため。pnpm のストアからハードリンクされるので約 1 秒)

コピー元になる main の `target/` は、ツールチェインの更新などで古い成果物が溜まると大きくなり、コピーが遅くなります。肥大化したら main で `cargo clean` してから `just ci` で作り直してください。

Claude Code では `task-start` スキルがこの手順を実行します。サブエージェントを `isolation: "worktree"` で起動すると `target/` のコピーが行われずビルドに時間がかかるので、オーケストレーターが `just wt-add` で worktree を作ってからワーカーに渡すことを推奨します。

### 3. 作業する

- 反復中は `just crate <name>` を使うと速く確認できます。
- `crates:` に書かれていないクレートの変更が必要になったら:
  - 小さな変更 (フィクスチャの追加、`pub` を付けるだけ、など) なら行ってよい。完了報告に明記する。
  - 公開 API の変更や設計に関わる変更なら、**手を止めて** タスクファイルの「メモ」に書き、状態を `blocked` にするか、新しいタスクを起票してオーケストレーターに知らせる。
- 仕様書と実装の食い違いを見つけたら、どちらが正しいかを判断して仕様書も直す。判断できない場合は、仕様書に `> 未決:` として書く。
- こまめにコミットします。コミットメッセージは **英語** の Conventional Commits 形式にします: `feat(runtime): add warp deformer evaluation (T0104)`。規約の詳細は [AGENTS.md#コミット](../../AGENTS.md#コミット) にあり、commit-msg フックで検査されます。フックを `--no-verify` で飛ばしてはいけません。

### 4. 完了を報告する

1. `git fetch` (リモートがある場合) の後、`git rebase main` で main に追従する。
2. `just ci` を通す。
3. タスクファイルを更新する: `status: review` にし、受け入れ条件のチェックボックスを埋め、「メモ」に要点 (やったこと、やらなかったこと、後続タスクの候補) を書く。
4. リモートがある場合は PR を作る。ない場合は、オーケストレーターにブランチ名を伝える。

Claude Code では `task-finish` スキルがこの手順を実行します。

### 5. マージする (オーケストレーター)

- `just ci` が通っていることを確認し、main に squash merge する。squash 後のコミットメッセージも英語の Conventional Commits 形式にし、タスク ID を含める。
- タスクファイルを `status: done` にする。
- worktree を片付ける: `just wt-remove T0104 --delete-branch` (未コミットの変更があれば git が削除を拒否する)

## 衝突を避けるための規約

| 衝突しやすい箇所 | 対策 |
| --- | --- |
| `Cargo.toml` の `[workspace.dependencies]` | 1 行 1 依存、アルファベット順。衝突したら両方の行を残す |
| `Cargo.lock` | 衝突したら main 側を採用し、`cargo check --workspace` で再生成する |
| `pnpm-lock.yaml` | 衝突したら main 側を採用し、`pnpm install` で再生成する |
| `ugoe-model` の型 | 型の追加・変更だけを行う小さな PR を先にマージし、実装はその後に行う (インターフェース先行) |
| `ugoe_model::fixtures` | 既存の関数を変更せず、新しい関数を追加する |
| `Command` enum | バリアントは enum の末尾に追加する |
| ADR の番号 | 後からマージする側が番号を振り直す |
| `docs/tasks/` | 自分のタスクファイル以外は、状態の欄に触らない |

## タスクの書き方 (オーケストレーター向け)

- 1 タスクは **1〜2 クレート、半日〜2 日程度** の大きさにします。これより大きいものは分割します。
- 受け入れ条件は、検証できる形で書きます (「〜のテストがある」「`just cli ...` が〜を出力する」)。
- 並行して進めたいタスクは、`crates:` が重ならないように切り分けます。
- 公開インターフェースの設計が必要なタスクは、「インターフェースのタスク」と「実装のタスク」に分けます。インターフェースのタスクを先に済ませておくと、実装のタスクを並行して進められます。
