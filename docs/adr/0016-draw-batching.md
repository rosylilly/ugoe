# 0016: 描画コストの自動最適化

- 状態: Accepted
- 日付: 2026-09-28
- 関連: [spec/rendering.md](../spec/rendering.md#描画の最適化)、ADR 0009、ADR 0002

## 背景

Cubism では、テクスチャ・合成モード・クリッピングの有無が前の描画と変わるたびに、描画の切り替えが発生して性能が落ちる。
さらに Cubism 5.3 の新機能は、オフスクリーン描画 > 高度な合成モード (クリッピングと同程度) >> 通常の合成モード、の順で重いとされている。
モデラーは性能のために表現を妥協している。ugoe は「同じ表現が軽い」ことを売りにする。

## 決定

1. **レンダラは、見た目を変えずに描画を自動で統合する。** 描画順で隣り合い、描画の状態 (テクスチャ・合成モード・マスクの内容・カリング) が同じ要素を、1 回の描画にまとめる。描画順は決して入れ替えない。
2. **要素ごとの値 (不透明度・乗算色・スクリーン色・マスクの係数) は、ユニフォームではなく頂点属性またはインスタンスのデータで渡す。** これにより、値が違う要素もまとめられる。
3. **ビルド時にテクスチャをアトラス化する。** 描画順で隣り合う要素が同じテクスチャを使うように、`ugoe build` がテクスチャをまとめる。
4. **マスクは GPU で処理し、変わらないフレームでは作り直さない。** マスクの内容 (ADR 0009) が前のフレームと同じなら、アトラスを再利用する (T0106 の変更フラグを使う)。
5. **最適化の効果を測れるようにする。** `FrameStats` に描画回数・状態の切り替え回数・転送量を出し、ベンチマークを CI で記録する。
6. 独自レンダラ (エンジン組み込み、portability.md の段階 B) 向けに、統合してよい条件を仕様として公開する。

## 検討した代替案

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| 描画順を並べ替えてまとめる | さらに描画回数が減る | 見た目が変わる。提案の条件 (見た目を変えない) を満たさない |
| モデラーに最適化を任せる (Cubism と同じ) | 実装が不要 | 差別化にならない |

## 結果

- 同じモデルでも描画回数が減り、特にモバイルや Web で有利になる。
- 要素ごとの値の渡し方が変わるため、シェーダと頂点の形式が変わる (参照レンダラの内部の変更)。
