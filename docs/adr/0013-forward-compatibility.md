# 0013: 前方互換と段階的な劣化

- 状態: Accepted
- 日付: 2026-09-28
- 関連: ADR 0004、ADR 0008、[spec/file-formats.md](../spec/file-formats.md#機能の宣言と段階的な劣化)

## 背景

Live2D では、新しいバージョンの Cubism で書き出したファイルを古いランタイムで読めない。
運用中のゲームやアプリはランタイムを簡単に更新できないので、これが採用の妨げになる。
ugoe は「新しいファイルを古いランタイムで読んでも、知らない機能だけを簡易な表示に落として動く」ことを仕様で保証する。

## 決定

1. **1.0 以降のファイル形式は、機能 (feature) の単位で拡張する。** 機能には安定した ID (例: `mask.intersection`、`physics.dynamic`、`lighting.normal_map`) を付ける。
2. **ファイルは、自分が使っている機能を宣言する。** 各機能は次のどちらかとして宣言する。
   - **任意 (optional)**: 知らないランタイムは、その機能について仕様が定める **フォールバック** を適用して読み込みを続ける。
   - **必須 (required)**: 知らないランタイムは読み込みを拒否し、足りない機能の ID を示すエラーを返す。
3. **新しい機能を追加するときは、仕様にフォールバックを必ず書く。** フォールバックを定義できない機能は必須として宣言する。書き出すツールは、必須の機能を使うときに警告を出す。
4. **データの符号化を、未知の値に耐えるようにする。**
   - 構造体の未知のフィールドは無視する (MessagePack のフィールド名付き表現と serde の既定の挙動で満たされる)。
   - 拡張されうる enum には「未知の値」を表すバリアントを持たせ、未知のタグを読んでもエラーにしない。その要素にはフォールバックを適用する。
5. **互換性をテストで保証する。** 各リリースのファイルを互換性テスト用の資料として保存し、新しい機能を含むファイルを古い読み込みルールで読むテストを CI で行う。
6. 1.0 より前は、この仕組みを実装して検証する期間とし、互換性は保証しない (ADR 0004 のとおり)。ただし仕組み自体は 1.0 より前に完成させる。

## フォールバックの例

| 機能 | 知らないランタイムでの扱い |
| --- | --- |
| 新しい合成モード | 通常の合成で描く |
| マスクの共通部分 | 和集合として扱う |
| 新しいデフォーマの種類 | 恒等変換として扱う (子は親の変換だけを受ける) |
| 動的物理の出力先 (ADR 0011) | その出力を無視する (揺れない) |
| 法線マップ (ADR 0015) | ライティングなしで描く |
| 着せ替えモジュールのスロット (ADR 0014) | スロットを無視し、本体だけを描く |

## 検討した代替案

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| バージョン番号だけで判断する (新しければ拒否) | 単純 | 提案の核心である「古いランタイムでも動く」を満たせない |
| 未知の要素をすべて無視する | 単純 | 表示が壊れても気づけない。機能ごとに意味のあるフォールバックを定義する方が安全 |

## 結果

- 運用中のアプリは、ランタイムを更新しなくても新しいモデルを (劣化した表示で) 読める。
- 機能を追加する作業に「フォールバックの定義」と「互換性テストの追加」が必ず含まれるようになる。
- `SCHEMA_VERSION` は、互換性を壊す変更 (必須機能でも表現できない変更) のときだけ上げる。
