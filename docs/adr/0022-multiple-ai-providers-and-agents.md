# 0022: 複数の AI プロバイダと、エージェントに判断を任せる経路

- 状態: Accepted (2026-09-29、利用者の判断)
- 日付: 2026-09-29
- 関連: ADR 0006 (AI は提案するだけ)、ADR 0020 (AI 支援を 1.0 に含める)

## 背景

M6 の AI 支援は、`ugoe_ai::Provider` (画像とテキストを送り、JSON Schema に沿う JSON を受け取る) の上に作ってあり、分類・リギング・法線マップの提案はモデルに依存しない。
一方で、実際に呼べるプロバイダは Anthropic の Claude API (`ClaudeProvider`) だけで、エディタのキーの保存と送信の同意の画面も Claude を前提にしている。
利用者は Claude Code だけでなく、OpenCode や ChatGPT など、ほかのモデルやエージェントも使えることを望んでいる。

## 決定

AI の判断をどこで行うかについて、次の 2 つの経路を両方とも用意する。

1. **エディタの中で API を呼ぶ経路 (プロバイダ):** `Provider` の実装を増やす。
   - Claude API (既存) に加えて、**OpenAI 互換の API** (Chat Completions と構造化出力・画像入力) のプロバイダを足す。
   - これ 1 つで OpenAI (ChatGPT のモデル)・OpenRouter・Gemini の OpenAI 互換の窓口・手元の Ollama / LM Studio / vLLM などを扱う。
   - 送り先が手元 (ループバック) なら `Destination::Local` とし、同意を求めない。
   - エディタの設定でプロバイダとモデルを選ぶ。API キーはプロバイダごとに OS の資格情報の保存先に置く。
2. **外部のエージェントに判断を任せる経路 (MCP):** `ugoe-mcp` に、自動リギングの各段階をツールとして出す。
   - レイヤーの画像を返すツール、分類の結果を受け取るツール、提案を作る・検証するツールなど。
   - AI の判断 (画像を見て分類する・パラメータを選ぶ) は、MCP クライアント側のエージェント (Claude Code・OpenCode・Codex CLI など) が自分のモデルで行う。ugoe は API キーを持たず、外部に何も送らない。
   - 提案の適用は ADR 0006 どおり、既存の `propose_edit` / `apply_proposal` と同じく利用者の確認を通す。
   - ChatGPT のように HTTP で MCP サーバにつなぐクライアントのために、stdio に加えて HTTP のトランスポートも用意する (別のタスク)。

既定のプロバイダは Claude のままとする (既存の利用者の設定を変えない)。

## 検討した代替案

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| プロバイダだけを増やす | エディタの中で完結する | 利用者が API キーと従量の費用を用意する必要がある。エージェントの契約を活かせない |
| MCP だけにする | ugoe が API を呼ばず、キーも持たない | エディタだけでは AI 支援が使えない。エージェントの動かし方に慣れていない利用者に難しい |
| 各社の API を個別に実装する | 各社の固有の機能を使える | 実装と保守が増える。OpenAI 互換の API で大半を覆える |

## 結果

- 利用者は、エディタの中で好きなプロバイダを選ぶか、手持ちのエージェントから MCP で動かすかを選べる。
- `ugoe-ai` のプロンプトと出力の JSON Schema は、特定のモデルに依存しないように保つ (モデルごとの調整は設定で行う)。
- 構造化出力に対応しないモデル・サーバでは、JSON の検証と再試行 (既存の仕組み) に頼る。
- M6 の受け入れテスト (T0510) の実際の API での確認は、どちらかの経路の 1 つで行えばよい。
