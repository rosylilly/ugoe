# 0035: 1.0 の範囲を、今進めている開発すべて (M1〜M11) の完了にする

- 状態: Accepted
- 日付: 2026-10-11 (利用者の決定)
- 関連: T0085 (この ADR)、ADR 0020 (「1.0 = M1〜M7 の完了」をこの ADR で置き換える。マイルストーンの順序と AI 支援の扱いは 0020 のまま)、
  ADR 0018 (ライセンスと、最初の 1.0 の範囲)、ADR 0028 (M8 は 1.0 に含める)、ADR 0031 (M11 の方針)、[roadmap.md](../roadmap.md#10-の範囲)

## 背景

ADR 0020 で 1.0 を「M1〜M7 の完了」とした。その後に足したマイルストーンの 1.0 との関係は、文書ごとにばらばらになっていた。

- M8 (スタジオと UI の基盤) は、利用者の決定で「1.0 に含める」とした (ADR 0028)。ロードマップの「1.0 の範囲」は M1〜M7 のままで、食い違っていた。
- M9 (コードレビュー) と M10 (UI のクオリティ) は「1.0 に含めるかは未決」、M11 (移植性) は 1.0 との関係を書いていなかった。
- M7 (配布と移植) は「1.0 の直前」としていたが、その後に M8〜M11 を進めたので、M7 は 1.0 の直前のマイルストーンではなくなった。

利用者は 2026-10-11 に、今進めている開発はすべて 1.0 に入れると決めた。

## 決定

- **1.0 = M1〜M11 の完了と、Release の作業。** M1〜M11 の各マイルストーンの「完了の条件」を満たし、Release のマイルストーン (公開の作業。
  時期は利用者が決める) を終えたものを 1.0 とする。ADR 0020 の「1.0 = M1〜M7 の完了」をこの ADR で置き換える。
- **M1〜M11 に置いたタスクは、完了の条件に含めない後続のタスクも 1.0 の範囲に入れる。** M9・M10 の「どれを 1.0 に含めるかは利用者が決める」は、
  この決定で「すべて含める」に決まった。1.0 から外すタスクは利用者が個別に決め、ロードマップの「1.0 の後の候補」に書く
  (最初の 1 つは Unreal のプラグイン T0407)。
- 実機・実際のエンジン・OS での人の手の確認 ([manual-check.md](../manual-check.md)) は、マイルストーンの完了の条件には含めない
  (各マイルストーンの完了の判断の節に、残る確認として書く)。1.0 の公開の前に、利用者が確認表のどこまでを確かめるかを決める。
- 1.0 で約束すること (ファイル形式の互換性は 1.0 から、AI 支援は提案の形式と採用の流れだけ) は ADR 0020 のまま変えない。

## 検討した代替案

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| 1.0 = M1〜M7 のまま、M8〜M11 は 1.0 の後とする | 範囲が小さい | 利用者の方針と合わない。M8 は 1.0 に含めると決めてある。M9 で見つけた不具合の修正を 1.0 の後に回すことになる |
| マイルストーンごとに 1.0 に含めるかを決める (今までのやり方) | 細かく選べる | 決めていないものが残り、文書の間で食い違う (今回の食い違いの原因) |
| 各マイルストーンの完了の条件だけを 1.0 の範囲にし、後続のタスクは外す | 1.0 が早く来る | 後続には細工した入力で止まる・データを失う種類の修正もあり、外すものを選ぶ判断が別に要る |

## 結果

- ロードマップの「1.0 の範囲」・M8〜M11 の節・アーキテクチャの設計判断の表を、この ADR に合わせて揃えた (T0085)。
- 1.0 までの範囲はさらに大きくなる。1.0 より前はファイル形式の互換性を保証しない (ADR 0004) ことは変わらない。
- 新しいマイルストーンを足すときは、1.0 に含めるかを足すときに決め、ロードマップの「1.0 の範囲」を同じ PR で直す。

## 追記: 公開の前の安定の扱い (利用者の方針 2026-10-11。T0095)

公開も 1.0 の日程も決まっていないので、API・ABI の版や挙動の安定には神経質にならず、よりよいソフトウェアに育てることを優先する。

- 公開 API (crates.io に出す 8 つのクレート)・C ABI・wasm と各バインディングの API・ファイル形式は、よりよい形が見つかれば変えてよい。
  移行の説明・互換の別名・semver の約束のための仕掛け (`unstable-` の feature・`#[non_exhaustive]` の揃え・約束に含めないという注記など) は作らない。
- 公開の範囲を狭める作業 (T0195 の洗い出し) は、約束のためではなく内部の整理として行う ([release.md#公開の範囲](../release.md#公開の範囲))。
- C ABI の版 (`ABI_VERSION`) は、壊したら上げる規則のまま使う (古いホストが黙って壊れないための安価な守り)。ただし、版を上げずに済ませる
  ためだけに不自然な形 (構造体を変えずに関数を足し続けるなど) を選ばない ([crates/ugoe-ffi/README.md](../../crates/ugoe-ffi/README.md#abi-の版))。
- 上の「1.0 で約束すること」(ファイル形式の互換性は 1.0 から) は変えない。1.0 で何を約束するかは、公開の時期を決めるときに見直す。
