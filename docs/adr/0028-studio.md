# 0028: 配信用のアプリ「スタジオ」(apps/studio) の範囲・構成・描画の場所・外部 API の安全性

- 状態: Accepted (2026-10-02、利用者の確認済み。仮想カメラの OS の部品・ホットキーの依存・M8 でやらないことは利用者の判断)
- 日付: 2026-10-02
- 関連: T0800 (この ADR)、T0801〜T0809 (スタジオの実装)、T0900 (共有 UI と i18n、ADR 0029)、T0904 (再生の層 `@ugoe/player`)、
  ADR 0003 (ビューポートは WebView の wasm)、ADR 0011 (動的物理)、ADR 0018・0019 (ライセンス)、ADR 0023 (エディタの MCP の待ち受け)、
  ADR 0025 (`@ugoe/runtime`)

## 背景

M8 で、配信で使う新しいデスクトップアプリ「スタジオ」を作る ([roadmap.md](../roadmap.md#m8-スタジオと-ui-の基盤))。
利用者が決めたことは次のとおりで、この ADR はこれを前提にする。

- M8 は 1.0 に含める。
- ビューア (`apps/viewer`) は、モデルを確かめるための薄いアプリのまま残す。配信の機能はスタジオに入れる。
- 画面の言語は日本語と英語から始める (仕組みは ADR 0029)。
- 外から操作する API は、ループバックだけ・トークン・利用者の許可・既定は切。他製品の API の名前は使わない。
- 配信ソフトへの出し方に、ウィンドウの取り込みのほか、仮想カメラ (Windows・Linux・macOS) と OBS のブラウザソース用の URL を含める。

決める必要があるのは、(1) ビューアとの役割分担とライセンス、(2) ウィンドウの構成、(3) 入力・シーン・プロファイルの置き場所、
(4) 出力ウィンドウ・仮想カメラ・ブラウザソースに **どこで描いた画を渡すか**、物理と時間をどこで回すか、
(5) 外部 API とブラウザソースの待ち受けの安全性、(6) M8 でやらないこと、である。

(4) の判断の材料として、いまの口は次のとおり。

- **`ugoe-render`:** デバイスもサーフェスも持たず、ホストから `Device`・`Queue`・`TextureView` を受け取って `Renderer::encode` で描く
  (AGENTS.md の規則 6)。テクスチャや法線マップ・光源は `Renderer` に持たせたまま、毎フレーム描ける。
- **`ugoe-headless`:** `prepare` → `Prepared::render(&Gpu)` は **1 枚を描く口** で、呼ぶたびに `Renderer` を作り、テクスチャを上げ直し、
  ターゲットを作って読み戻す (`crates/ugoe-headless/src/gpu.rs`)。CLI と MCP の静止画には十分だが、毎秒 60 回描く用途にはそのままでは使えない。
  `Gpu` (サーフェス無しのアダプタとデバイス) と、乗算済みアルファの変換・読み戻しの手順は使い回せる。
- **`@ugoe/runtime` (`WebPuppet`)・ビューア:** WebView の中で `Puppet` の更新と描画を両方行う。`read_pixels()` で別のテクスチャに描いて
  RGBA を読み戻せる (ビューアの画像の保存、T0420)。`set_parameter`・`set_enabled(stage, bool)`・`set_tracking`・`set_lip_sync_level` がある。
- **`Puppet` の決定性:** 同じモデルと、同じホストの操作の列と同じ `dt` の列からは、同じパラメータの値とパーツの不透明度が得られる
  ([spec/motion.md](../spec/motion.md#フレーム内の適用順))。物理は固定ステップで積分し、乱数を使わない (ADR 0011)。
- **動的物理 (ADR 0011):** 物理の出力先はパラメータだけでなく、回転デフォーマの角度・デフォーマの平行移動・頂点でもある。
  **パラメータの値だけを送っても、受け手は揺れを再現できない** (受け手が物理を回す必要がある)。
- **WebView の制約:** 隠れたり最小化されたりした WebView は `requestAnimationFrame` とタイマーを絞られる (T0804 で切る)。
  WebView から Rust へ画素を渡すには IPC を通る。1920×1080 の RGBA は 1 枚 8.3 MB で、60 fps では約 500 MB/s になる。

## 決定

### 1. 役割分担とライセンス

- スタジオは **配信者が配信中に使うアプリ** で、`apps/studio` (Rust のクレート `ugoe-studio`、npm パッケージ `@ugoe/studio`) に置く。
  ビューアは **作者が `.ugoe` を確かめるアプリ** のまま、出力ウィンドウ・仮想カメラ・ブラウザソース・外部 API・グローバルなホットキー・
  プロファイルを持たない。どちらにも要る再生の層 (読み込み・モーション・表情・トラッキング・ライティング・着せ替え) は
  `@ugoe/player` (`packages/player`、T0904) に置いて共有する。
- **ライセンスは GPL-3.0-only** (エディタ・ビューアと同じ。ADR 0019 の理由がそのまま当てはまる)。`scripts/check-licenses.mjs` の
  `EDITOR_CRATES` に `ugoe-studio` を入れる (T0801)。MIT の `@ugoe/runtime` を使ってよい。アプリ同士で import はしない
  (ビューアのコードを写すのはよい。共有するなら `packages/` に切り出す)。
- **依存の層:** Rust のバックエンドは、ランタイム層と `ugoe-headless` (ランタイム層だけに依存するツール層) に依存してよい。
  エディタの中核 (`ugoe-editor-core`) や AI には依存しない (スタジオはモデルを編集しない)。`scripts/check-layers.mjs` に登録する (T0801)。

### 2. ウィンドウの構成

- **操作ウィンドウ:** シーン・入力・表情とモーション・出力・外部 API の設定を置く。**モデルを描かない** (描画は出力に任せ、
  GPU の負荷を出力の分だけにする)。様子は出力の画ではなく、パラメータの値・入力の状態・負荷の数値で示す。
- **出力ウィンドウ:** モデルだけを描く。枠なし・背景の透過・最前面 (切り替え)・大きさのプリセット (1920×1080 など)。
  UI の要素を一切重ねない (OBS のウィンドウの取り込みにそのまま使う)。閉じても、仮想カメラとブラウザソースは止まらない。
- どちらのウィンドウも WebView のバックグラウンドの抑制を切る (T0804)。入力 (カメラ・マイク) は操作ウィンドウの WebView で取るので、
  操作ウィンドウを最小化しても入力が止まらないようにする。

### 3. 描画の場所と、物理と時間の扱い

**決定: パラメータを決める場所を 1 つにし (指揮役)、描く場所は出力ごとに置く。指揮役はフレームごとに「パラメータの値と `dt`」を配り、
受け手はそれを同じ順に適用して自分で物理を回し、描く。** 検討した (a)〜(d) の比較は下の「検討した代替案」。

- **指揮役 (conductor):** スタジオのバックエンド (Rust) の専用のスレッドに、ネイティブの `ugoe::Puppet` を 1 つ置く。
  モーション・表情・トラッキング・目パチ・呼吸・リップシンク・外部 API からの値をここで適用し、`update(dt)` する。
  **物理の段は切る** (`Toggles::physics = false`)。描かない (GPU を使わない)。
  - 物理を切った `update` の後のパラメータの値は「物理の前の値 + リップシンク」になる。これを受け手が基準値として書けば、
    受け手の物理は指揮役で物理を回した場合と同じ入力を受け取る。
  - WebView の外で回すので、ウィンドウの抑制の影響を受けない。ホットキー・外部 API・ブラウザソースの待ち受けもバックエンドにあるので、
    入力から指揮役までに WebView を通らない (カメラとマイクを除く)。
  - 刻み (tick) は出力のフレームレート (30 / 60 / 120) で回す。`dt` は実測し、0.1 秒で頭打ちにする (止まっていた後に大きく飛ばない)。
- **フレームの配信 (stream):** 1 刻みごとに `{ seq, dt, values }` を配る。`values` はモデルのパラメータの定義順の `f32` の並び
  (100 個で 400 バイト)。このほか、シーンの状態 (モデル・着せ替えの組・ライティング・位置と大きさと回転・背景) が変わったときに、
  版の番号 (`revision`) 付きの「シーン」の通知を配る。物理をリセットする出来事 (着せ替え・モデルの読み直し) も、どの `seq` で行うかを載せて配る。
- **受け手 (follower):** 目パチ・呼吸・リップシンクの段を切り、モーション・表情・トラッキングを使わない `Puppet` (wasm かネイティブ) を持つ。
  届いたフレームを **1 つずつ順に**、`values` を書き込んで `update(dt)` する (物理とポーズの段だけが動く)。描くのは最後のフレームだけ。
  - 追記 (T0133・T0134): 実装では、フレームは `{ seq, dt, values, lip_sync }` で、`values` は物理の段に入る直前の値、`lip_sync` は音量と強さ。
    受け手は `Puppet::follow(values, lip_sync, dt)` で 基準値の書き込み → 物理 → リップシンク → ポーズ → 評価 の順に進める (1 つの Puppet と同じ段の順)。
    詳しい形は docs/studio.md と docs/spec/motion.md の「受け手として進める」を正とする。
  - こうすると、すべての受け手の物理は同じ値の列と同じ `dt` の列で進むので、**物理を含めて同じ形になる** (決定性)。
    受け手の描画のフレームレートは物理に影響しない。ネイティブと wasm の三角関数などの差で、ごく小さな違いは残りうる (許容誤差で比べる)。
  - 遅れて届いたフレームはまとめて順に適用する (飛ばさない)。接続が切れていて抜けた `seq` があれば、最新のシーンの通知から作り直し、物理はリセットする。
- **出力ごとの描画の場所:**

  | 出力 | 描く場所 | 受け取り方 |
  | --- | --- | --- |
  | 出力ウィンドウ | 出力ウィンドウの WebView の wasm (`@ugoe/player` の受け手のモード) | Tauri の `Channel` (順序を保つ) |
  | ブラウザソース | OBS のブラウザ (CEF) の中の `@ugoe/runtime` (wasm。WebGPU が無ければ WebGL2) | ループバックの WebSocket (トークン付き) |
  | 仮想カメラ | バックエンドのネイティブの受け手 + `ugoe-render` (オフスクリーン、読み戻し) | 同じプロセスのチャネル |

  - 仮想カメラの受け手は、`ugoe-headless` の `Gpu` を使い、`Renderer` とテクスチャを持ち続けて毎刻み描く **常駐の描画の口** を使う
    (`ugoe-headless` に足す。1 枚を描く今の口は変えない)。読み戻しはステージングのバッファを 2〜3 枚回して待たない。
    カメラの API が求める形 (NV12・YUY2 など) への変換は GPU で行ってから読み戻す (読み戻しの量も半分になる)。
    仮想カメラを止めている間は、この受け手を作らない (GPU を使わない)。
  - 3 つの出力は互いに独立で、使っている出力の分だけ描画の負荷がかかる。出力ウィンドウを閉じても仮想カメラとブラウザソースは続く。
- **遅れ:** カメラのトラッキングからの遅れは、ビューア (同じ WebView で更新と描画) より「IPC の 1 往復 + 最大 1 刻み」増える
  (60 刻みで最大約 17 ms + 1〜2 ms)。トラッキングの入力が届いたら次の刻みを早める調整は、実装で測ってから決める (T0803)。

### 4. 入力・シーン・プロファイル

- **入力:** カメラのフェイストラッキング (`@ugoe/face-tracking`、MediaPipe) とマイクの音量は、操作ウィンドウの WebView で取り、
  結果 (トラッキングの入力の JSON・音量の 0〜1) を IPC で指揮役に送る (1 フレーム 1 KB 未満)。
  ホットキーはバックエンドでグローバルなショートカットとして受ける (アプリが前面に無くても効く)。外部 API も指揮役に届く。
- **シーン:** モデル・付けるモジュール・ライティング・位置と大きさと回転・背景 (透過・単色・クロマキー・画像) の組。
  1 つのシーンにアバターは 1 体。切り替えは指揮役が受け、受け手にシーンの通知を配る。
- **プロファイル:** シーンの一覧・ホットキーの割り当て・出力の設定・入力の機器の選択を、版の番号付きの JSON の 1 ファイルに保存する。
  アプリの設定であって、モデルのファイル形式 (`docs/spec/file-formats.md`) ではない。形式は [docs/studio.md](../studio.md) に書く (T0802)。
  モデルのパスは絶対パスで持ち、見つからなければ選び直させる。

### 5. 配信ソフトへの出し方

| 出し方 | 透過 | 何をするか |
| --- | --- | --- |
| ウィンドウの取り込み | あり (OS と配信ソフトによる) | 出力ウィンドウを取り込ませる。手順は OS ごとに docs に書く (T0804) |
| ブラウザソースの URL | あり | スタジオがループバックで HTTP を待ち、ページ・モデルのファイル・フレームの配信を出す。URL を OBS のブラウザソースに入れる (T0808) |
| 仮想カメラ | なし (背景で埋める) | カメラの機器として出す。会議アプリでも使える。Windows (Media Foundation、Windows 11)・Linux (v4l2loopback) は T0807、macOS (Camera Extension) は T0809 |

- 仮想カメラは **利用者が開始したときだけ** 動かす。透過は出せないので、シーンの背景 (透過のシーンは単色) で埋める。
- 仮想カメラに要る OS の部品 (Windows の COM のメディアソースの登録、Linux の v4l2loopback、macOS の System Extension と署名) の扱いは
  下の「8. 仮想カメラの OS の部品と `unsafe` の例外」。

### 6. 外部 API とブラウザソースの待ち受けの安全性

外部 API (T0805) とブラウザソース (T0808) は、1 つの HTTP の待ち受けを共有してよいが、**有効にするスイッチとトークンは別** にする。

- **既定は切。** 操作ウィンドウで利用者が有効にしたときだけ待ち受ける。待ち受けている間は操作ウィンドウに常に示す。
- **ループバックだけ。** `127.0.0.1` (と `::1`) にだけ束ねる。ほかのアドレスに束ねる設定は M8 では持たない。
- **トークン。** OS の乱数で 256 ビットを作り、プロファイルとは別の場所 (アプリのデータの場所) に保存する。作り直せる (作り直すと古いものは無効)。
  比較は定数時間。外部 API は最初のメッセージ (またはヘッダ) で、ブラウザソースは URL のパスで渡す (OBS はヘッダを付けられない)。
- **利用者の許可 (外部 API)。** トークンを持つクライアントでも、初めて接続したときは名前を名乗らせ、操作ウィンドウで利用者が承認するまで
  何もさせない。承認したクライアントには、そのクライアント用の鍵を渡し、以後はそれで接続する (一覧から取り消せる)。
  承認のときに **権限** (読むだけ / 操作する) を選ばせる。
- **ブラウザソースの URL のトークンは、読むだけ。** ページ・モデルのファイル・フレームの配信だけを受け取れ、操作はできない。
  モデルのファイルは、今のプロファイルのシーンが使うものだけを出す (任意のパスを読ませない)。
- **ブラウザやトンネルからの悪用を防ぐ** (`ugoe-mcp` の `--http` と同じ考え方): `Host` がループバックの名前でない要求と、
  プロキシ・トンネルの転送ヘッダ (`X-Forwarded-For`・`Forwarded` など) が付いた要求は `403`。`Origin` が付いた WebSocket の接続は、
  スタジオが出すページ自身の `Origin` 以外を `403` (DNS リバインディングと、開いた Web ページからの接続を防ぐ)。
- **値の上書きは期限付き。** 外部 API でパラメータの値を設定するときは期限 (既定 1 秒) を持たせ、期限を過ぎたら上書きをやめる
  (クライアントが落ちても値が残らない)。続けて動かすクライアントは送り続ける。
- **名前:** API は「スタジオの操作 API」(英語では ugoe Studio API) と呼び、メッセージと操作の名前は ugoe の言葉で付ける。
  他製品の API の名前・メッセージの名前・既定のポートを真似ない (互換を名乗らない)。
- 形は WebSocket の上の JSON-RPC 2.0 (要求・応答と通知)。メッセージは JSON Schema で定め、英語の API リファレンスを書く (T0805)。
  操作は [docs/studio.md](../studio.md#外部-api) と英語のリファレンス [docs/studio-api.md](../studio-api.md) (T0805)。

### 7. M8 でやらないこと

- 複数人のコラボ (別の計算機のアバターを並べる・同期する)
- 配信サイトのイベント (コメント・ギフト・フォローなど) との連携。必要なら外部のツールが外部 API で行う
- プラグイン (スタジオの中で第三者のコードを動かす)
- 1 つのシーンに複数のアバター、小物 (アイテム) を後から置くこと
- 顔以外のトラッキング (手・体)、ネイティブのカメラの取り込み
- 配信・録画そのもの (RTMP・ファイルへの書き出し)。配信ソフトに任せる
- 外部 API のループバック以外への公開 (LAN の別の計算機からの操作など)
- 他製品の API との互換
- マニュアルの英訳 (画面は日英。マニュアルは日本語から)

### 8. 仮想カメラの OS の部品と `unsafe` の例外

- **Windows (T0807):** Windows 11 の Media Foundation の仮想カメラ (`MFCreateVirtualCamera`) で出す。OS のサービス (Frame Server) が
  読み込む COM のメディアソースの DLL を作り、**インストール時に管理者の権限で登録する** (スタジオの実行中には権限を求めない)。
  Windows 10 など使えない版では、理由を出して開始しない。代わりの手段として「OBS でスタジオを取り込み、OBS の仮想カメラを使う」手順も docs に書く。
- **`unsafe` の例外:** COM のインターフェースを実装し、OS から呼ばれる関数を出すには `unsafe` が避けられない。
  **例外は仮想カメラ専用の 1 クレート (Windows のメディアソースと、スタジオからの画の受け渡し) だけ** に許す
  (AGENTS.md の規則は「`ugoe-ffi` と、この ADR で決めた仮想カメラの 1 クレート」)。そのクレートは次を守る。
  - `unsafe` を COM と OS の境界 (インターフェースの実装・ポインタの受け渡し・共有メモリ) に閉じ込め、境界の外へは安全な API だけを出す。
    `unsafe` のブロックには、成り立たせている前提を `// SAFETY:` のコメントで書く。
  - スタジオのバックエンド (`ugoe-studio`) 本体と、ほかのクレートでは `unsafe` を禁止のままにする。Linux と macOS の受け渡しに `unsafe` が
    要るときも、同じクレートに置く (新しい例外を作らない)。
  - ワークスペースの lint (`unsafe_code = "deny"`) を、そのクレートの `Cargo.toml` だけで上書きする。
  - ライセンスは GPL-3.0-only (スタジオの一部)。依存は GPL-3.0 と両立するものに限る。
- **Linux (T0807):** v4l2loopback の機器に書く。**スタジオは v4l2loopback を入れない** (カーネルモジュールで、入れるには管理者の権限が要る)。
  機器が無いときは入れ方 (ディストリビューションごとのパッケージと `modprobe` の引数) を案内するだけにし、自動で `sudo` しない。
- **macOS (T0809):** CoreMediaIO の Camera Extension (System Extension) で出す。実装と、署名・公証・entitlement の手順は M8 で作るが、
  **配布物に入れるのは、利用者が Apple Developer Program のアカウントを用意してから** にする (署名の名義は Release のマイルストーンで決める)。
  それまでの macOS では、ウィンドウの取り込みとブラウザソースを案内する。

### 9. グローバルなホットキー

- Tauri 公式の `tauri-plugin-global-shortcut` (MIT / Apache-2.0) を使う。
- Wayland では、アプリが前面に無いとグローバルなショートカットを受けられない。Wayland の利用者には、外部 API (Stream Deck などのツール)
  で同じ操作をすることを docs で案内する。

### 10. 一致の検査

「受け手は同じフレームの列から同じ形を作る」(3.) を、次のテストで確かめる。

- **同じ入力の列で頂点が一致する (T0801・T0808):** 物理を使うフィクスチャ (`ugoe_model::fixtures` の揺れもの) に、決めた入力の列
  (パラメータの値と、揃っていない `dt` を混ぜた列。モデルの読み直しと物理のリセットを含む) を指揮役に与え、出てくるフレームの列を記録する。
  その列を (1) ネイティブの受け手、(2) wasm の受け手 (`@ugoe/player` の受け手のモード)、(3) ブラウザソースのページの受け手に順に適用し、
  各フレームの後の頂点 (`drawable_positions`) とパーツの不透明度を比べる。wasm どうしは完全一致、ネイティブと wasm は許容誤差付きで比べる。
- **指揮役で物理を回した場合と同じになる:** 同じ入力の列を、物理を有効にした 1 つの `Puppet` で進めた結果と、指揮役 + 受け手の結果を比べる
  (許容誤差付き)。物理を切った指揮役の値を基準値として書く手順 (3.) が正しいことを確かめる。
- **描画の頻度に依らない:** 受け手が 1 フレームずつ描いた場合と、数フレームまとめて適用してから描いた場合で、最後の頂点が一致する。
- **画の一致 (T0808):** 配信を止めた状態 (同じ `seq`) で、出力ウィンドウとブラウザソースのページを画像で比べる (ヘッドレスの Chrome。許容誤差付き)。
  仮想カメラの画は、ネイティブの受け手の読み戻しを同じ `seq` の出力ウィンドウの画と比べる (GPU のテスト、`just test-gpu`)。

## 検討した代替案

### 描画の場所

| 案 | 負荷 | 遅れ | 一致の度合い | 実装の量 | 依存 |
| --- | --- | --- | --- | --- | --- |
| **(採用) 指揮役がパラメータと `dt` を配り、受け手が物理を回して描く** (c を物理まで含めて決定的にしたもの) | 配る量は 1 フレーム 1 KB 未満。描画は使っている出力の分だけ。更新 (CPU の変形) は指揮役と受け手の数だけ | IPC の 1 往復 + 最大 1 刻み | 物理を含めて同じ形 (ネイティブと wasm の小さな差だけ) | 指揮役・配信の形・`@ugoe/player` の受け手のモード・常駐の描画の口 | 新しい依存なし |
| (a) バックエンドで `ugoe-render` (wgpu) を使ってオフスクリーンに描き、すべての出力に画を渡す | GPU の描画は 1 回。ただし出力ウィンドウ (WebView) へは画素を渡すことになり (b) と同じ重さ。ブラウザソースへは透過付きの動画の符号化が要る | 読み戻しと符号化で 1〜2 フレーム | 1 枚の画なので完全に一致 | 常駐の描画・透過付きの符号化 (重い)・出力ウィンドウへの転送 | 動画の符号化器 |
| (a') (a) で、出力ウィンドウを WebView ではなく wgpu のネイティブのサーフェスにする | GPU の描画は 1 回 | 最小 | 完全に一致 | 透過する枠なしのネイティブのウィンドウを 3 つの OS で作る (Windows の DirectComposition、Linux のコンポジタ依存など)。`@ugoe/player` と画面の部品を使えない | ウィンドウの層の追加の依存 |
| (b) 出力ウィンドウの WebView で描いた画を読み戻して IPC で渡す | 1080p60 で約 500 MB/s の IPC と、毎フレームの読み戻しによる GPU の待ち | 読み戻し + IPC で 1〜3 フレーム | 出力ウィンドウと完全に一致 | 小さい | なし |
| (c) 評価後のパラメータの値だけを送り、受け手はそれぞれの時計で物理を回す | 採用案と同じ | 採用案と同じ | 揺れが受け手ごとにずれる (動的物理の出力はパラメータではないので送れない) | 採用案より少し少ない | なし |
| (d) 出力ウィンドウの WebView を指揮役にし (ビューアと同じく 1 か所で更新と描画)、そこからパラメータを配る | 採用案と同じ | 出力ウィンドウは最小 | 採用案と同じ | 最小 (ビューアの層をそのまま使う) | なし |

- (a) は仮想カメラには向く (採用案でも仮想カメラの受け手はこの形) が、出力ウィンドウとブラウザソースに画を渡す部分が重い。
- (b) は 1080p60 で IPC が重く、出力ウィンドウを隠すと止まる問題も抱える。
- (c) は動的物理 (ADR 0011) の揺れを受け手ごとに勝手に進めるので、出力ごとに揺れが合わない。採用案は (c) の配る形を保ち、
  `dt` を一緒に配って全フレームを順に適用することで、物理まで一致させた。
- (d) は実装が最も少ないが、出力ウィンドウを閉じる・隠すと仮想カメラとブラウザソースも止まる。仮想カメラだけを使う利用者
  (会議アプリ) にも出力ウィンドウを開かせることになる。

### 外部 API

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| 他製品の API と互換にする | 既存のツール (Stream Deck のプラグインなど) がそのまま使える | 利用者の決定 (他製品の API の名前は使わない) に反する。相手の変更に追従し続ける必要がある |
| トークンだけ (利用者の許可なし) | 手間が少ない | トークンが漏れると、利用者が気付かないうちに操作される。利用者の決定に反する |
| HTTP の要求・応答だけ (WebSocket なし) | クライアントが簡単 | シーンの変化などの通知を受け取れない (ポーリングになる) |

## 結果

- 出力ウィンドウ・ブラウザソース・仮想カメラが同じ指揮役から同じフレームの列を受け取るので、どれで取り込んでも同じ動きになる。
  T0808 の「ページの画が出力ウィンドウと同じ」は、配信を止めた状態 (同じ `seq`) で許容誤差付きで比べられる。
- 指揮役はバックエンドにあり、WebView の抑制に左右されない。出力ウィンドウを閉じても、ほかの出力は続く。
- 受け手は全フレームを順に `update` するので、描画のフレームレートを下げても CPU の更新の回数は刻みと同じだけかかる。
  出力のフレームレートの設定は「刻みの速さ」になり、出力ウィンドウを刻みより速く描いても新しい形は出ない (T0804 の「無制限」は
  「120 刻み」などに読み替える必要がある)。
- 受け手は「書き込んだ値を基準値にする」ために、`Puppet` の「前のフレームの出力と違う値を基準値にする」規則
  ([spec/motion.md](../spec/motion.md#フレーム内の適用順)) に頼る。送った値が前のフレームの出力とビット列で同じだと基準値にならない。
  受け手どうしの一致は保たれる (同じ入力なら同じ結果) が、明示的に基準値を書く口 (`Puppet` に足す) が要るかを T0801 で確かめる。
  要るなら、ランタイムの公開 API の変更なので別のタスクにする。
- 仮想カメラのために `ugoe-headless` に常駐の描画の口を足す。ツール層のクレートの変更だが、CLI と MCP の 1 枚の口は変えない。
- 外部 API とブラウザソースは既定で切で、ループバック・トークン・利用者の許可に守られる。外部 API のための追加の手間
  (初回の承認) が利用者に増える。
- 見直すきっかけ: 受け手の数が増えて CPU の更新が重くなったとき (指揮役で物理まで回し、デフォーマの出力を配る形を検討する)、
  `Puppet` の決定性が崩れる変更が入ったとき、OBS のブラウザソースで WebGL2 が使えない環境が多いと分かったとき。
