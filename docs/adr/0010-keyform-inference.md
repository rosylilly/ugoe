# 0010: キーフォームの推定 (組み合わせ爆発の解消)

- 状態: Accepted
- 日付: 2026-09-28
- 関連: [spec/keyform-inference.md](../spec/keyform-inference.md)、[spec/model.md](../spec/model.md)、ADR 0005、ADR 0006

## 背景

Live2D 系のリギングで最も時間がかかるのは、キーフォームの組み合わせを 1 つずつ手で作る作業である。
たとえば `AngleX` (3 キー) × `AngleY` (3 キー) × 表情 (2 キー) なら 18 個の形が必要になる。
しかしそのほとんどは「端の形の組み合わせ」や「左右の鏡像」や「立体を回した見え方」で、機械的に推定できる。
ugoe が乗り換えの理由を作るうえで、ここが最大の突破口になる。

## 決定

1. **キーフォームの各セルに「手で作った (authored)」か「推定した (derived)」かの区別を持たせる。**
   推定したセルは、推定の元になったセルが変わると作り直す。手で修正したセルは authored になり、以後は上書きしない。
2. **推定はツール層で行い、結果をキーフォームとして焼き込む。ランタイムは推定を知らない。**
   ランタイムの評価 ([spec/evaluation.md](../spec/evaluation.md)) は変えない。どのランタイム実装でも同じ結果になり、性能にも影響しない。
3. 推定の方法は次の 3 つから始める。いずれも決定的なアルゴリズムで、AI は必須ではない。
   - **加算合成**: 軸ごとの変化 (基準の形からの差分) を足し合わせて、斜めや組み合わせのセルを作る。
     例: `AngleX=30, AngleY=30` = 基準 + (`AngleX=30` − 基準) + (`AngleY=30` − 基準)。
   - **ミラー**: 左右の対になるパラメータ・メッシュ・デフォーマについて、片側の形を対称軸で反転してもう片側を作る。1 つのメッシュの中での左右対称 (顔の輪郭など) も扱う。
   - **深度からの回転**: 頂点ごとの深度 (奥行き) を持たせ、疑似 3D として回転・投影して、顔や体の振り向きのキーフォーム (中間と斜めを含む) を作る。深度は手で塗るか、原画から AI で推定する (ADR 0006 に従い提案として出す)。
4. 推定は `ugoe_editor_core::Command` として実行する (ADR 0005)。Undo でき、AI やスクリプトからも同じ操作ができる。
5. アルゴリズムは新しいツール層のクレート `ugoe-rigging` に置く。エディタ・CLI・AI が共通に使う。

## 検討した代替案

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| ランタイムで推定する (欠けたセルを実行時に合成する) | ファイルが小さい | すべてのランタイム実装に推定ロジックが必要になる。移植先ごとに結果がずれる危険がある。手修正との合成規則が複雑になる |
| ブレンドシェイプ (加算変形) だけで表現する | 仕組みが単純 | 「斜めだけ少し直したい」といった局所的な修正ができない。深度からの回転のような非線形な変化を表せない |
| AI だけで推定する | 表現力が高い | 再現性がなく、オフラインで使えない。決定的な基盤を先に作り、AI は深度推定などの入力づくりに使うのがよい |

## 結果

- 作業量は「軸ごとの端の形」だけになり、組み合わせの数に比例して増えなくなる。
- ファイルには焼き込んだキーフォームが入るので、容量は従来と同じ。推定の設定 (方法・深度など) はオーサリング用のデータとして持ち、ランタイムは読み飛ばす (ADR 0013 の任意機能)。
- 推定の品質は、見た目の比較テスト (`ugoe render` の画像) で検証する。
