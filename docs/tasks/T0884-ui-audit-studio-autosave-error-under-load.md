# T0884: ui-audit の autosave-error の場面の揺れ

## 目的

T0880 の確認で、`just ui-audit` (3 つのアプリをまとめて流す重い回) の強制色 (forced colors) の回で、スタジオの `-autosave-error` の場面が
「知らせが出ない」(自動の保存の失敗の帯が出ない) と落ち、そのまま全体が時間切れになった。`just ui-audit --only studio` を流し直すと通る。
負荷で帯を待つ時間 (`tests/ui-audit/lib/apps.mjs` の `autosaveFailureScene` まわり。帯や前の知らせを待つ 5 秒) が足りないと見られる。
重い回でも場面が安定して通り、1 つの場面の失敗で全体が止まらないようにする。

## 受け入れ条件

- [ ] 落ちる原因を確かめた (帯を待つ時間・自動の保存の時機 (変えてから約 0.8 秒)・前の場面の知らせが閉じる待ち・強制色の回だけで起きる理由)。
      確かめ方 (CPU に負荷をかけて `--only studio` を流す、まとめて流すなど) と結果をメモに書いた
- [x] 帯を待つ処理を負荷に強くした (固定の待ち (`waitForTimeout`) を条件の待ちにする、待つ時間を延ばす、自動の保存を偽のホストから直に起こす、など。
      選んだ案と理由をメモに)
- [x] 場面が失敗したとき、全体が時間切れにならずに、その場面の失敗として報告して次へ進む (か、すぐに失敗で終わる)。時間切れの扱いを直した
- [x] `just ui-audit` (3 つのアプリをまとめて) を少なくとも 2 回流して、スタジオの `-autosave-error`・`-autosave-denied` が通ることを確かめた
- [x] tests/ui-audit/README.md の該当の説明を直した (待ち方を変えたなら)
- [x] `just ci` が通る

## メモ

- T0089 で起票した (元の候補: T0880 (ui-audit のスタジオの -autosave-error の場面が、3 つのアプリをまとめて流す重い回の強制色で「知らせが出ない」と落ちて
  時間切れになった。`--only studio` では通る。帯を待つ 5 秒を負荷に強くするか、時間切れの扱いを直す))。
- M8 の後続 (docs/roadmap.md の M8 の「後続のタスク」)。番号はスタジオの帯 (T0874 と同じ)。
- スタジオの画面のコード (apps/studio) を変える必要が分かったら (自動の保存の時機など)、案をメモに書いて止まる。
- 確かめたこと (原因。1 つ目の受け入れ条件は、帯が出なかった場面の失敗そのものを再現できなかったのでチェックしていない):
  - 帯の出る速さ: `autosaveFailureScene` に待った時間を出す一時の計測を入れて、`--only studio --variants forced` を流した。
    ロードアベレージ 33 の機械で 0.8〜1 秒。CDP の `Emulation.setCPUThrottlingRate` で CPU を 8 倍に遅くしても 0.95〜1.05 秒、
    48 の空回りのプロセスを足してロードアベレージ 55 にしても 0.83〜1.3 秒 (同じ回の強制色の組の Tab のたどりは 206 秒まで遅れた)。
    自動の保存 (0.8 秒) の後の仕事は小さく、負荷で 5 秒を使い切るとは考えにくい。強制色の組だけで遅い様子も無かった。
  - 前の場面の知らせ: 承認の知らせが閉じるのを待つ所 (`detached`) は、どの回も落ちなかった。偽のホスト (`setHotkeys` の送り直し・
    `saveProfile`) と `Autosave` (同じ失敗の知らせを繰り返さない・書き換えないプロファイルで止まる) を読んだが、帯を出さなくなる
    競り合いは見つからなかった。T0880 の回の画像・ログは残っておらず、帯が出なかった原因は分からないまま。
  - 時間切れ: 3 つのアプリをまとめると、混んだ機械ではビルドとエディタ (407 秒) だけで 600 秒を超え、スタジオに入る前に Bash の上限で
    殺された (1 回目の試し)。場面の失敗は既に報告して次の組へ進んでおり (失敗で待つのは帯の 5 秒と画像だけ)、T0880 の「時間切れ」は
    場面の失敗のせいではなく、全体の長さが Bash の 600 秒を超えたためと見る (強制色の組はスタジオの最後の組なので、時間切れの直前に当たる)。
- やったこと (案: 待つ時間を延ばす + 失敗の手がかり + 時間の上限):
  - 帯と承認の知らせが閉じるのを待つ上限を 5 秒から 20 秒に (`NOTICE_TIMEOUT_MS`)。出るまでの条件の待ちなので、通る回は遅くならない。
    固定の待ちは元から無く、偽のホストから自動の保存を直に起こす案は画面の時機 (Control.svelte の `AUTOSAVE_MS`) を迂回して撮る場面の
    意味が変わるので採らなかった。帯が出なかったら、待った時間と画面にある帯 (トーンと文) を失敗の文に添える (次に起きたときの手がかり)。
  - 組ごとの時間の上限 `--variant-timeout` (既定 480 秒、0 で上限なし): 過ぎたらコンテキストを閉じて、その組を
    `timed out after …s (--variant-timeout; last scene: …)` の場面の失敗にし、次の組へ進む (止まったページで全体が止まらない)。
  - 全体の締め切り `--deadline <秒>` (起動から数える。既定なし): 過ぎたら流している組を閉じ、残りの組を飛ばして (報告に `deadline` の
    エラーとして載せる)、報告と summary を書いて終了コード 1。上限のある所から流すときに、殺されて報告が残らないことが無いように。
    既定を付けなかったのは、人が流すときに 10 分を超えても全部撮ってほしいため。
  - 道具: `lib/limits.mjs` (`withTimeLimit`・`deadline`・`secondsOption`) と単体テスト (`test/limits.test.mjs`。上限を過ぎた後の本体の失敗を
    捨てること、止めたことで本体が先に失敗しても上限の失敗を返すこと)。tests/ui-audit/README.md と docs/testing.md の「UI の監査」の時間の説明。
  - `--variant-timeout 15` で組が時間切れの失敗になって次へ進むこと、`--deadline 0.001` で 16 の組を飛ばして報告を書き終了コード 1 になることを流して確かめた。
- `just ui-audit` (3 つまとめて) を 2 回: どちらも終了コード 0、3 つのアプリともエラー 0、スタジオの `-autosave-error`・`-autosave-denied` は
  15 の組 (dpr2 は開いた画面だけ) のすべてで通った (強制色の 2 組も)。かかった時間は 664 秒と 630 秒 (エディタ 407・394 秒) で 600 秒を超えるので、
  切り離して流し、前面で終わりを待った。
- 起票の候補:
  - ほかの場面の 5 秒の待ち (`waitFor({ timeout: 5000 })`。ダイアログ・メニュー・Popover など) も、混んだ機械で揺れるなら同じ上限にまとめる。
  - 混んだ機械で 3 つのアプリをまとめると 600 秒を超えるので、エージェントの手順 (AGENTS.md の表・multi-agent.md) で `--deadline` を付けるか、
    アプリごとに `--only` で流すように案内する (今回は README と docs/testing.md に書いただけ)。
