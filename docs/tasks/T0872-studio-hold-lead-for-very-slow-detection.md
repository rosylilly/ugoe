# T0872: スタジオ: 値が 1 秒に 1 個より少ないときも促しを寄せ続ける

## 目的

`Pacer` は、直近の `LEAD_WINDOW` (1 秒) に値が届いていなければ促しを寄せるのをやめ (`aim` が `None`)、促しを刻みの直後に戻す
(apps/studio/src-tauri/src/pacing.rs の `aim`)。T0868 で見積もりに使う値は 10 個・5 秒まで残すようにしたが、この「戻す」判定は 1 秒のままなので、
検出がとても重く値が 1 秒に 1 個より少ない (例: 1.5 秒に 1 個) ときは、値が届くたびに寄せては次の値の前に戻すのを繰り返し、
寄せた促しの効果が出ない (T0868 のメモの「やらなかったこと」)。戻すまでの時間を値の間隔で決め、とても重い検出でも寄せ続ける。

## 受け入れ条件

- [x] 促しを戻すまでの時間を、直近の値の間隔から決めた (例: 直近の値の間隔の中央値の 2 倍か `LEAD_WINDOW` の大きいほう、上限は `LEAD_MAX_AGE`)。
      決めた式と理由を `pacing.rs` のコメントと docs/studio.md#入力 に書いた。刻みのたびの確保を増やさない
- [x] 仮の時刻のテスト (`simulate_with` と T0868 の `Detector`) で、値が 1 秒に 1 個より少ない場合 (例: 検出 1,200 ms と 2,000 ms、刻み 30・60・120) に
      寄せたままになることと、遅れた値の割合が前より下がるか変わらないことを確かめた。前と後の数をメモに書いた
      (遅れた値の割合は、同じ物差しの「使われた値の待ちの平均」と「4 ms より前に届いた値の割合」に読み替えた。メモの「受け入れ条件の 2 つ目の読み替え」)
- [x] トラッキングが止まった (値が来なくなった) ときは、今と同じく上限の時間の後に促しを戻す (テストで確かめた)
- [x] 値が多い場合 (T0864・T0868 のテスト: `margin_grows_when_sleeps_wake_late`・`widely_varying_detection_does_not_leave_many_values_late`・
      `few_values_from_slow_detection_are_rarely_late`・`old_leads_are_dropped_when_detection_changes`) の数が変わらないか良くなる
- [x] `just e2e --only studio` が通る
- [x] `just ci` が通る

### やったこと (claude-worker-T0872)

- `pacing.rs` の `Pacer`: 促しを刻みの直後に戻すまでの時間 (`hold`) を、値が届くたびに `hold_for` で決め直す。
  見る値 (`leads`) の届いた間隔の **中央値の 2 倍** を `LEAD_WINDOW` (1 秒) 以上 `LEAD_MAX_AGE` (5 秒) 以下に収めたもの。
  `aim` は `LEAD_WINDOW` の代わりにこれを見る。間隔はスタックの配列 (`MAX_LEADS` 個) に集めて `select_nth_unstable` で中央値を取るので、
  確保は増えない (刻みのたびではなく値が届くたび)。値が 1 秒に 2 個以上なら 1 秒のまま。
  比べるため、`hold` を 1 秒のままにする `Pacer` (T0872 の前と同じ) をテストで作れるようにした (`hold_by_interval` の欄)。
- **`MAX_PULSES` を 64 → 600 にした** (120 刻みで 5 秒分。先に確保)。64 個では、60 刻みで約 1 秒・120 刻みで約 0.5 秒より前の促しを忘れ、
  検出 1,200 ms の値がどの促しのものか分からないので、そもそも測れず寄せられなかった (`hold` だけ変えても 60・120 刻みでは効かない)。
  探すのは値が届くときだけ (線形、最大 600)。
- 式と理由は `pacing.rs` のコメント (`hold_for`・`MAX_PULSES`) と docs/studio.md#入力 の「促しを戻すまでの時間」。

### 受け入れ条件の 2 つ目の読み替え (利用者が案 A を選んだ)

- 「寄せたままになること」は満たした (寄せていない刻みが 0)。
- 「遅れた値の割合が前より下がるか変わらないこと」は、**同じ物差し (使われた値の待ちの平均と、余裕の上限 4 ms より前に届いた値の割合) で比べる** 形に
  読み替えてチェックを付けた。どちらも 30・60 刻みで下がり、120 刻みでは前とほぼ同じ (待ちは ±0.5 ms のうち。上の表)。
- 読み替えた理由: 「遅れた値」(T0863 の定義) は、促しが狙った刻みに遅れた値を数える。寄せていない促しの値には狙った刻みが無いので数えない。
  とても重い検出では、検出を始める促しがいつも寄せる前に戻っていたので、前はどの値も数えられず 0% だった。後は寄せた値をすべて数えるので、
  見積もりに使う値が 5 秒の間の 2〜3 個しか無い分の外れが 11〜26% 出る。字面のまま比べると、前の 0% (数えていない) と後の数を比べることになる。
- そのため、とても重い検出では操作ウィンドウの「刻みに遅れた値」の表示が **0% から 1〜2 割に変わる** (値が悪くなったのではなく、前は数えていなかった値を
  数えるようになった)。docs/studio.md#入力 の「促しを戻すまでの時間」にも書いた。
- 検討した案: A (今の形で受け入れる。利用者が選んだ)、B (値がとても少ないとき見積もりに使う値の古さの上限を延ばす。下の起票の候補)、C (T0872 の前に戻す)。
  B は試しに上限を 40 秒にすると遅れた値が 0〜11.5% に、待ちもさらに縮んだ (30 刻み 1,200+0〜8 ms で 6.61 → 5.61 ms) が、検出の重さが変わったときに
  古い値を長く見る (T0868 で 5 秒にした理由と相反する) ので、このタスクでは入れていない。

### 起票の候補

- 値がとても少ない (1 秒に 1 個より少ない) とき、見積もりに使う値の古さの上限 (`LEAD_MAX_AGE` 5 秒) を値の間隔で延ばして (例: 10 個そろう長さ、
  上限 40 秒)、狙った刻みに遅れる値を減らす (案 B。上限 40 秒で遅れた値 11〜26% → 0〜11.5%)。検出の重さが変わったときに古い値を長く見ない工夫
  (T0868 の 5 秒の理由) と合わせて決める。
