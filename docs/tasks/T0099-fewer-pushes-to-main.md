# T0099: push の回数を減らす運用

## 目的

T0091 で push ごとの CI を軽くした (キャッシュが当たって 1 回 約 35 分、外れて約 70 分) が、push が月 40 回ほどあると軽い CI だけで
約 1400〜2800 分になり、GitHub Actions の無料枠 (3000 分) に近い。オーケストレーターの運用か CI の起動の条件で、push の回数か
1 回あたりの分を減らす。

**判断が要る (利用者)。** 運用の変更なので、着手したら下の案と推奨を利用者に確かめてから文書とワークフローを直す。

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | オーケストレーターが main への push をまとめる (手元の main に squash merge を重ね、push は決まった区切り (例: 1 日に 1〜2 回、または並行の 1 回り (起票の 1 回分) が終わったとき) だけ) | ワークフローを変えない。今の運用 (手元で `just ci` を通してからマージ) のまま | push までの間、手元の main だけが進む (機械が壊れると失う。ほかの機械で作業しにくい) |
| B | PR を通す運用にし、PR の CI を必須の検査にして、PR を通したものは main への push で流し直さない (`push` の起動をやめるか、`rust-checks` だけにする) | 公開した後の運用 (Rulesets・外の人の PR) と同じ形になる | タスクごとに PR を作る手間。PR ごとに CI が流れるので、PR の数が多いとかえって増える |
| C | push の CI を `rust-checks` (ビルドしない検査) だけにし、ビルドとテストは定期 (例: 毎晩) と PR・手動にする | push の数に関係なく分が小さい | 壊れた main に気づくのが翌日になる。手元の `just ci` に頼る |

- **推奨: A** (公開するまで)。マージの前に手元で `just ci` を必ず通しているので、push ごとの CI は「手元と CI の環境の違い」を見るだけで、
  まとめて流しても見落としは増えない。公開してからは B に移る (docs/release.md#人がすること の Rulesets と合わせる)。
- B に移るなら、必須の検査の名前のまとめ方もここで決める (今は `ci.yml` の `rust` がまとめのジョブ。`release-checks.yml` は PR で動かないので
  必須の検査にはできない。T0091 の候補「release-checks の結果を 1 つにまとめるジョブ」はこの形のときだけ要る)。

  **やったこと:**
  - docs/workflow/multi-agent.md の「5. マージする」に「main を push する区切り」を足した。公開するまではマージのたびに push せず、
    並行の 1 回りをマージし終えたとき・1 日の作業を終えるとき (main が進んでいれば)・タグを打つ前とほかの機械や人に渡すときに
    まとめて push する (多くても 1 日に 1〜2 回。手元の main だけが進む期間を 1 日を超えて溜めない)。push の前に手元の main で `just ci`、
    push の CI が落ちたらすぐ直す。公開してからは PR を通す運用に移り、`ci.yml` の `rust`・`web`・`rust-checks` を必須の検査にする。
  - docs/testing.md#ci-のジョブ に、push をまとめる運用への参照を足した。
  - docs/release.md#人がすること に「PR の運用へ移る」段を足した (必須の検査の名前と、公開の前に手元の main を push し終えること)。
  - ワークフローは変えていない (案 A はワークフローを変えない)。`release-checks.yml` は PR で動かないので必須の検査にしない。
    T0091 の候補「release-checks の結果を 1 つにまとめるジョブ」は要らない (公開後の必須の検査は `ci.yml` の既存のジョブで足りる)。

  **見積もり (課金の分。T0091 のメモの数: push 1 回は `ci.yml` だけで、キャッシュが当たって約 35 分・外れて約 70 分、定期の
  release-checks は月 約 420〜660 分):**
  - push の回数は、1 日に 1 回・月の作業日を約 20 日とすると月 約 20 回 (多い月でも 1 日に 2 回まで、約 30〜40 回)。
  - 月 20 回: push 約 700〜1400 + 定期 約 420〜660 = 約 1100〜2100 分。月 30 回: 約 1050〜2100 + 定期 = 約 1500〜2800 分。
    T0091 の見積もり (月 40 回で約 1800〜3500) より下がり、キャッシュが外れ続けなければ無料枠 (3000) に収まる。リリースのある月は
    約 600 が足される。まとめた push は scripts/・.github/・Cargo.lock を含みやすく、絞り込みはほとんど効かない前提で数えた。
  - 確かめていないこと: GitHub Actions が止まっているので、実際の月の課金では確かめていない。

  **起票の候補:** なし (公開の作業 (T0096 など) で PR の運用へ移るときに、Rulesets の必須の検査の名前を実際の CI の名前と合わせる)。
