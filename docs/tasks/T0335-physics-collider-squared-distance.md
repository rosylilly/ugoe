# T0335: 性能: 物理の衝突の判定で、距離を平方根を取らずに 2 乗で比べるか決める (判断が要る)

## 目的

T0333 で、掃引の間は変わらない親と衝突体の距離を 1 度だけ求めるようにした (結果のビット列は変えていない。物理そのものがネイティブで約 1 割、
wasm で約 15% 速くなった)。物理そのものの残りの大半は、掃引と二分法のたびの `WorldCollider::blocks_from` の算術
(`point_segment_distance(q, a, b) < radius + margin` と `segment_segment_distance(parent, q, a, b) < radius`。どちらも平方根を含む) である
(crates/ugoe-physics/src/collider.rs)。距離を 2 乗のまま比べれば (`d2 < (radius + margin)^2` など) 平方根が要らなくなり、
物理そのものがネイティブ・wasm ともさらに 1〜2 割速くなる見込み (T0333 のメモ)。ただし境目の判定の丸めが変わるので、
結果のビット列が変わりうる。急がない。

## 判断が要る

2 乗で比べても、判定は数学的には同じで、`std` の有無や OS で結果が変わらない (掛け算と足し算は IEEE 754 で決まる。ADR 0031 の目的は保てる)。
変わるのは、境目 (距離がほぼ `radius + margin`) で当たりかどうかが、丸めの違いで入れ替わりうること。掃引と二分法は不連続なので、1 度入れ替わると
その後の粒子の位置が大きく変わりうる (docs/spec/physics.md の例は境目の場面を含めないとしている)。

- **案 A (推奨。測ってから決める): 2 乗で比べる形を試し、物理そのものが 1 割以上速くなれば入れる。** 物理の golden
  (`golden_tests.rs`。T0333 の `colliding_chain_matches_recorded_hash` を含む) を記録し直す。リリース前なので、前の版と同じビット列を保つ必要は無い
  (利用者の方針)。1 割に満たなければ入れず、測った数をメモに書いて終える (案 B と同じ結果)。
- 案 B: 入れない。ビット列を保つ。物理そのものは 1 フレームの評価のうち小さい (T0193・T0334 の段の内訳で、生成のモデルの `update` 約 54µs の
  うち約 5µs) ので、全体では数 % にしかならない。
- 案 C: `point_segment_distance` を使う粒子の判定 (`blocks_from` の 1 つ目の条件と `push_out` の前の判定) だけを 2 乗にし、
  `segment_segment_distance` (区間どうしの距離) はそのまま残す。変える式を減らすが、ビット列が変わりうるのは A と同じ。

推奨は A。決まった物差し (物理そのものの時間) で入れるかを決め、効かなければ入れない。入れるなら、判定の式がどこで平方根を取らないかを
仕様に書く必要は無い (数学的に同じ判定なので) が、境目の丸めが実装で決まることは docs/spec/physics.md#衝突体 に書く。

### 結果 (claude-worker-T0335)

**結論: 入れなかった。** 2 乗で比べる形を試したが、物理そのものの速さはネイティブで約 5〜7%、wasm で 0〜6% (揺れの範囲) で、
決めた物差し (1 割以上) に届かなかった。コードは main と同じに戻し、測った数だけをここに書く (案 B と同じ結果。ビット列・golden・仕様は変わらない)。

**試した形** (変更は scratchpad の `t0335/squared.patch` に残した。リポジトリには入れていない):

- `WorldCollider::blocks_from` の 2 つの判定を、距離の 2 乗で比べる `within(d2, reach)` (`reach > 0.0 && d2 < reach * reach`) にした。
  `point_segment_distance_squared`・`segment_segment_distance_squared` を足し、親の距離 (掃引の始めに 1 度) と `push_out`
  (もともと 2 乗で比べている) はそのまま。`reach` が 0 以下・NaN のときは先に弾き、前の判定 (`d < reach` が偽) と同じになることを
  単体テストで確かめた (無限大は、距離の 2 乗が `f32` を溢れない範囲で前と同じ。`reach` の 2 乗が 0 に潰れるほど小さい
  `f32::MIN_POSITIVE` などは前と違って当たらなくなる。境目の丸めの一種)。
- ビット列: 物理の golden は衝突体のある `colliding_chain_matches_recorded_hash` だけが変わった (`0xc32b8ae439d502fe` → `0x54f5265b2836028b`)。
  ほかの golden と既存のテストはそのまま通った。T0193 の作業用クレートの 1,200 フレームのハッシュは、生成のモデルが
  `e9b9cf0fb09082ce` → `ba165652fb387b49` (ネイティブと wasm で一致)、`avatar.ugoe` は `ab157425c0847d11` のまま (衝突体が無い)。

**速さ** (前 = main の 260c9361 を別の worktree に置いたもの、後 = 2 乗で比べる形。同じ条件で続けて交互に測った。AMD Ryzen 9 7900・WSL2、
ほかのワーカーのビルドが並行して load average 8〜13、2026-10-09 08:04〜08:06 に 3 回。測り方は T0333 と同じ):

- `physics_timing` の `dynamic_hair` の `physics itself` (最も速いもの、µs): 1 回目 0.62・0.61・0.60 → 0.59・0.59・0.59、
  2 回目 0.60・0.63・0.62 → 0.59・0.60・0.59、3 回目 0.62・0.61・0.67 → 0.58・0.60・0.59 (約 4%)。
- T0193 の段ごとの計測 (生成のモデル、物理そのもの = `update_instance` から 1 段目を除いたもの、200 フレームの平均の最速 / 中央値、µs):
  - ネイティブ: 1 回目 4.99/5.55・5.01/5.57・4.96/5.50 → 4.66/5.13・4.67/5.22・4.61/5.15 (最速で約 7%)。
    3 回目 4.96/5.54・4.91/5.57・4.95/5.52 → 4.65/5.34・4.54/5.33・4.94/5.55 (約 0〜8%)。2 回目は揺れが大きかった (5.62・5.24・5.38 → 4.66・5.06・5.12)。
  - wasm (ヘッドレスの Chrome 154、3 回の中央値): 1 回目 5.95/6.80 → 5.95/6.60、2 回目 6.08/8.10 → 5.80/8.18、3 回目 6.08/7.30 → 5.70/7.55 (0〜6%)。
  - `avatar.ugoe` は物理そのものが 0.3µs ほどで変わらない。
- `puppet_timing` の `physics stages` の生成のモデルの `physics itself`: 5.4・6.1 → 5.8・5.6 (1 回目)、5.5・5.8 → 5.2・5.1 (3 回目)。
  `update` 全体は 50µs 台で、違いは揺れに埋もれる。

**見込みより小さかった理由 (推測):** T0193 で平方根が CPU の命令 (`f32.sqrt`・`sqrtss`) になったので、1 回は 1ns ほどで、パイプラインで
ほかの算術と重なる。判定 1 回の残りは、点と線分の距離の内積・割り算・`clamp` と、掃引の標本ごとの `Vec2::from_angle` (正弦と余弦) で、
2 乗にしても減らない。

**やらなかったこと:**

- 案 C (粒子の判定だけ 2 乗) は、A の全体でも 1 割に届かないので試していない。
- コードを入れていないので、golden の記録し直し・docs/spec と spec/ の更新・適合テストの参照の記録し直しはしていない。
  `just nostd-check`・`just wasm-check`・`just perf`・`just conformance` も、ライブラリのコードが main と同じなので流していない (`just ci` だけ)。

**起票の候補:** なし (掃引の標本ごとの正弦と余弦を、刻みの回転を掛けていく形にするなどの手は、ビット列が変わり、効くかも測っていない。
物理そのものは 1 フレームの 1 割ほどなので、今は急がない)。
