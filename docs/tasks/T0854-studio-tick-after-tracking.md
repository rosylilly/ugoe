# T0854: スタジオ: トラッキングが届いたら次の刻みを早める

## 目的

スタジオでは、操作ウィンドウがカメラのトラッキングの値を IPC で指揮役に送り、指揮役は決まった間隔の刻み (30・60・120 回/秒) で
`Puppet::update` を回して受け手に配る。値が刻みの直後に届くと、次の刻みまで (60 刻みで最大約 17 ms) 待つので、カメラからの遅れは
ビューアより「IPC の 1 往復 + 最大 1 刻み」多い (ADR 0028 の 3. の「遅れ」、docs/studio.md#入力 の「次の刻みを早める調整はしていない」)。
値が届いたら次の刻みを前に寄せて、この「最大 1 刻み」を縮める。

刻みの時刻がずれても、指揮役は実測の `dt` を配り受け手はその `dt` で物理を回すので、受け手どうしの形は揃う
(docs/studio.md#刻みの速さと正確さ)。崩れうるのは動きの滑らかさ (`dt` の揺れ) と負荷なので、そこを測って決める。

### やり方の候補 (作業者が測って選ぶ。公開の形は変わらないので利用者の判断は要らない)

- **a. 位相を合わせる:** 値が届いたら、次の刻みの予定をその時刻 (+ 小さな余裕) へ寄せる。刻みの速さは変えず、カメラ (30 / 60 fps) の
  フレームの直後に刻みが来るように少しずつ揃える。`dt` の揺れが小さい。
- **b. すぐに刻む:** 値が届いたら、前の刻みから一定の間隔 (例: 刻みの間隔の半分) 以上経っていればすぐ刻み、次の予定をそこから数え直す。
  遅れは最も小さいが、カメラと刻みの速さが違うと `dt` が揺れ、刻みの速さが設定を超えうる。

推奨は a (滑らかさを崩さずに、遅れの平均を下げる)。

### やったこと (claude-worker-T0854)

- **選んだ形 (a・b のどちらでもない):** 刻みは動かさず、操作ウィンドウへの入力の処理の促し (`subscribe_pulse`) を刻みの前へ寄せた。
  操作ウィンドウは促しを受けて検出する (`pulse.ts`・`FaceTracker` の `schedule`) ので、値が届く時刻は「促し + 検出と IPC」で決まる。
  a・b のように刻みを値へ寄せると、寄せた刻みの促しがまた検出を呼び、検出と IPC が刻みの間隔より短い限り刻みが設定より速くなる
  (刻みの速さを超えずに刻みの位相を合わせる置き場所が無い)。促しを動かせば、刻みの格子・速さ・`dt` は前と同じまま、値を刻みの約 1 ms 前に届けられる。
- 刻みのスレッドの本体を `apps/studio/src-tauri/src/ticker.rs` (`TickHost` を受けて回す) に移した。`lib.rs` の `run_ticks` は `ticker::run` を呼ぶだけ。
  時刻の決め方は `pacing.rs` の `Pacer` のまま (時計とスレッドを持たない): `wake(now)` が次に起きる時刻とすること (促しか刻み) を返し、
  `pulse(now)` が促しの番号を返し、`arrived(at, seq)` が促しから届くまでの時間を覚える。
- 促しには番号を付けた (Channel のメッセージが番号になる)。`pulse.ts` の `Pulse.current` が処理中の促しの番号を持ち、`Control.svelte` は
  トラッキングの値に番号を添えて `set_tracking(frame, pulse)` に送る (検出は促しの処理の中で同期して終わる)。番号が無いと、検出が刻みの間隔より
  重いときに「どの促しの値か」を取り違え、促しを動かすたびに測った時間もずれて寄せる先を追いかけ続けた (仮の時刻のテストで確かめた)。
- 寄せる量は、直近の約 1 秒の「促しから届くまで」のうち、値が刻みで使われるまでの待ちの合計が最も小さいもの。最大に合わせると、
  混んで 1 回だけ間隔より長くかかった値で寄せる先が 1 刻み近く回り、ほかの値が刻みに遅れた (最初の測定で 60/30 の p95 が 10 ms に悪化した)。
- 単体テスト (`pacing.rs`): 届いていなければ促しは刻みの直後・届くと次の刻みの (届くまで + 1 ms) 前へ動く・揺れたときと 1 回だけ遅いときの選び方・
  検出が間隔より重いとき・知らない番号を無視する・覚える数の上限・仮の時刻で 3 秒回して刻みの間隔がいつも設定のままで値が刻みの 1 ms 前に届く
  (30・60・120 刻み × 検出 2・6・12・20・45 ms)・届かなくなると促しが刻みの直後に戻る。`pulse.test.ts` に番号のテスト。
- docs/studio.md#入力・#刻みの速さと正確さ、ADR 0028 の 3. の「遅れ」に一言足した。`just e2e --only studio` は 13 件とも通った。

### 測ったもの

`ticker.rs` の `measure_tracking_wait` (`#[ignore]`。`cargo test -p ugoe-studio --lib ticker -- --ignored --nocapture`)。本物の `ticker::run` を実時間で回し、
偽の操作ウィンドウ (別のスレッド) が促しを受けて、カメラ (30・60 fps の格子) に新しいフレームがあれば `UGOE_TRACKING_COST_MS` (検出と IPC) 眠ってから値を届ける
(`Pulse.beat` と同じく、前の処理にかかった時間が経つまでは促しを飛ばす)。各組 5 秒、最初の 1 秒を除く。「前」は番号を添えない (= 促しを寄せない、変更前と同じ刻み)。

条件: 24 コアの WSL2 (Linux 6.18)、ほかのワーカー約 8 つが並行してビルド中で load average 9〜17、debug ビルド。変更の前のコミット
(68561b58 の時点。促しは刻みの直後) でも同じ表の「前」と同じ値 (待ち ≈ 間隔 − 検出) を確かめてある。

検出と IPC 6 ms (待ちの平均 / p95 / 最大 ms):

| 30 | 30 | 27.21 / 27.26 / 27.30 | 0.98 / 1.03 / 3.43 | 30.00 / 30.00 | 33.40 / 38.66 |
| 30 | 60 | 27.19 / 27.26 / 27.42 | 1.32 / 1.10 / 32.54 | 30.00 / 30.00 | 38.73 / 37.11 |
| 60 | 30 | 10.37 / 10.60 / 11.02 | 1.45 / 1.21 / 19.29 | 60.00 / 60.00 | 18.23 / 19.78 |
| 60 | 60 | 10.43 / 10.67 / 12.35 | 1.53 / 3.38 / 16.36 | 60.00 / 59.93 | 18.53 / 21.77 |
| 120 | 30 | 2.31 / 2.33 / 7.33 | 1.00 / 1.06 / 3.60 | 119.97 / 119.99 | 11.92 / 15.35 |
| 120 | 60 | 2.25 / 2.35 / 8.49 | 1.33 / 5.11 / 8.39 | 119.88 / 119.98 | 11.62 / 12.69 |

検出と IPC 2 ms: 前の平均は 31.2 (30 刻み)・14.6 (60)・6.2 (120) ms、後は 0.9〜1.3 ms。12 ms: 前は 21.2・4.6・4.5 ms、後は 0.9〜1.1 ms。

- 待ちの平均は「刻みの間隔 − 検出と IPC」(刻みの間隔の余り) から約 1 ms (`LEAD_MARGIN`) に縮んだ。最大は、混んだ計算機でスリープが数 ms 遅れて
  値が刻みに遅れたときの 1 刻みで、前と後で変わらない (前は待ちがもともと長いので遅れが最大に出にくい)。
- `dt` の揺れ・負荷の表示: 実際の刻みの速さはどの組も設定の 99% 以上 (注意は 95% 未満)、最も長い間隔は設定の 2 倍未満 (注意は 2 倍超)。
  `dt` の最小・最大の揺れは前と後で同じ程度 (どちらも計算機の混み具合によるもの)。刻みの格子は動かさないので、促しを寄せても `dt` は変わらない
  (仮の時刻のテストで、刻みの間隔がいつも設定と等しいことを確かめた)。
- トラッキングを使わないとき (値が届かない・番号が無い) と、外部 API のパラメータの上書きだけのときは、促しは刻みの直後のままで、刻みは前と同じ
  (`pulse_follows_the_tick_without_tracking`、測定の「前」の行がその経路)。トラッキング中は刻みのスレッドが 1 刻みに 2 回起きる (促しと刻み)。

### やらなかったこと・確かめていないこと

- 実際のカメラと MediaPipe での待ちは測っていない (偽の操作ウィンドウだけ)。実機でどれだけ縮んで見えるかは利用者の確認に残す。
  カメラの映像のフレームから促しまでの待ち (最大 1 刻み) と、検出そのものの時間は変わらない。
- 口パクの音量 (`set_lip_sync_level`) は番号を添えていない (計算は軽く、促しの直後に届くので、トラッキングに寄せた促しで一緒に刻みの前に届く)。
- Windows・macOS では動かしていない (スリープの粒度が粗いと、1 ms の余裕では刻みに遅れる値が増えうる)。

### 起票の候補

- 「フレームレートと負荷」に、値が届いてから刻みで使われるまでの待ち (平均と最大) を出す (実機で確かめるため。今はテストの中だけで測っている)。
- `LEAD_MARGIN` (1 ms) を、Windows・macOS で測って OS ごとに決める (遅れて 1 刻み待つ値の割合を見て)。
