# T0553: PSD: PackBits の展開の確保の上限 (入力の 64 倍) を見直す

## 目的

T0531 で PSD のデコードに資源の上限を入れた。PackBits の展開は確保を入力の 64 倍まで許すので、実質の目安は合計の上限 (4 GiB) になる。
小さな悪意のファイルで大きな確保を起こせないか、より厳しい上限 (例: 平面ごとに幅 × 高さから決まる大きさを先に確かめ、それを超える確保をしない) にできるかを検討する。

## 受け入れ条件

- [x] PackBits の展開で確保する大きさを、ヘッダの幅・高さから決まる大きさで抑えた (またはしない理由をメモと README に書いた)
- [x] 小さな入力から大きな確保を起こそうとするファイルのテストがあり、上限のエラーで止まる
- [x] `crates/ugoe-psd/README.md` の上限の説明を更新した
- [x] `just ci` が通る

## メモ

- T0019 で起票した (元の候補: T0531 の PackBits)。

### やったこと

- 調べた結果: T0531 の時点で、PackBits の平面の確保 (`rows * width`) は矩形から決まる大きさそのもので、`decode_plane`・
  `parse_composite` が確保の前に `Budget` (上限) と比べていた。残っていた穴は、(1) 行のバイト数の表を入力より大きく確保できる、
  (2) 64 倍の検査が全行の合計なので、短い行 (嘘) を長い行で補えば検査を通って平面を確保してから壊れた入力と分かる、の 2 つ。
- `decode_rle` で、表 (1 行 2 バイト) が残りの入力より大きければ確保せずに `Invalid` (truncated)、どの行も
  `2 * ceil(幅 / 128)` バイト (PackBits で書ける最も短い長さ) 以上なければ平面を確保せずに `Invalid` にした
  (合計の 64 倍の検査はこれに含まれるので置き換えた)。
- 64 倍より厳しくはしなかった。64 倍は PackBits の本当の最大の比 (2 バイト → 128 バイト) で、単色のレイヤーを最も縮めた
  正しいファイルはこの比になる。理由を README の「PackBits (T0553)」に書いた。
- テスト: 単体で行の長さ・表の大きさ。結合 (`tests/import.rs`) で、最も縮めた正しい PackBits のレイヤー 16 枚 (約 1.2 MiB で
  64 MiB を宣言) が合計の上限で止まること、矩形だけ大きく行の短いチャンネル (40000 × 40000 は上限のエラー、上限を外すと
  行の長さで `Invalid`。30000 × 30000 は上限に収まるが行の長さで `Invalid`)。

### やらなかったこと

- 確保しないことそのもの (確保の大きさ) はテストで測っていない (数える global allocator は `unsafe` が要るため)。
  確保の前に弾く経路を通ることを、エラーの種類とメッセージで確かめた。
